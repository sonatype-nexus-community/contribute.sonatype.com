## What Lifecycle reads

PHP is a **manifest** ecosystem and the documentation describes one file only: "files named `composer.lock` (a JSON file generated by PHP composer) will be analyzed". It does not scan `composer.json` or the `vendor/` directory. Sonatype recommends generating and committing `composer.lock` before scanning, so the Project must **commit `composer.lock`**.

## Tier 1 job

```yaml
  prepare-scan-input:
    name: Prepare Lifecycle scan input
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - name: Checkout
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false

      - name: Gather scan input
        run: |
          mkdir scan-input
          cp composer.lock scan-input/

      - name: Upload scan input
        uses: actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2
        with:
          name: lifecycle-scan-input
          path: scan-input/
          if-no-files-found: error
          retention-days: 3
```

This job runs nothing from the Pull Request, and does not need `composer install`.

## What you give up

- **Only top-level packages.** Sonatype's documentation says "only top-level dependencies (specified under the 'packages' group) are evaluated". Development dependencies, which Composer records under `packages-dev`, are not.
- **No binary scan** is documented for PHP.
- **Advisory only at PR time**, as for every ecosystem. A Pull Request that edits `composer.lock` is changing the thing being scanned.
